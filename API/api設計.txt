#１．製造するシステムの整理

##１－１．システムの登場人物と役割を整理する。

	機能、画面、利用者、業務ルールを横断的に整理する。

##１－２．業務の流れを整理する。

	提案、審査、差戻、監査などの流れと権限を整理する。

#２．API一覧作成

	基本設計書からAPI候補を抽出する方法として次の観点で、各機能を確認します。
		画面を開くときに取得するデータは何か。
		一覧検索や絞り込みで必要なデータは何か。
		登録・更新・削除するデータは何か。
		承認・差戻し・再提出など、業務状態を変更する操作は何か。
		操作権限を判断するために必要な情報は何か。
		監査で確認すべき履歴は何か。
			例えば「審査画面」には、審査対象一覧取得、提案詳細取得、審査履歴取得、審査実行など、複数のAPIが必要になる可能性があります。
			この段階では、APIのURLを先に決めるよりも、画面や業務操作に必要なデータと処理を洗い出すことを優先します。
	
	画面操作、データ取得・更新、業務処理からAPIを抽出し、重複と不足を確認する。
	URL、メソッド、JSON、型、必須条件、エラー、認証、状態遷移を定義する。

##２ー１．業務機能ごとに分類し、API名と主な処理を洗い出す。

##２－２．洗い出したAPIを整理しながら、API名とメソッドとエンドポイントを書き出し、一覧化する。

	メソッド：GET、POST,PUT,DELETE
	エンドポイント：/api/v1/proposalsや/api/v1/proposals/{proposalId}/review-assignments


	列名				記載内容
	API ID				API-001などの一意なID
	機能分類			提案管理、審査管理、監査など
	API名				提案詳細取得APIなど
	HTTPメソッド		GET、POST、PUT、PATCH、DELETE
	エンドポイント		/api/v1/proposals/{proposalId} など
	概要				APIが実行する処理
	利用者				提案者、審査者、事務局
	入力概要			パス、クエリ、リクエストボディ
	出力概要			レスポンスの主要項目
	認証・権限			必要な権限
	基本設計書の参照元	根拠となる資料
	詳細設計状況		未着手、作成中、レビュー中、合意済み
	備考・未決事項		確認事項や設計上の前提


	API ID		機能分類	API名						メソッド	エンドポイント
	API-001		共通		ログインユーザー情報取得	GET			/api/v1/me
	API-002		提案管理	提案一覧取得				GET			/api/v1/proposals


	APIを切り出す際の判断基準
		APIは、単純に画面の数だけ作るものではありません。
		データを取得する処理は、GETを基本とする。
		新規登録や、業務上の操作を実行する処理は、POSTを基本とする。
		既存データの一部更新にはPATCH、全体置換にはPUTを検討する。
		削除にはDELETEを検討する。ただし、業務上の取下げや取消しは専用の操作APIにする場合がある。
		承認や差戻しは、単純な項目更新ではなく業務ルールを伴うため、専用の操作APIとして設計する。


#３．APIの詳細設計

##３－１．リクエスト仕様

　例としてリクエストは提案IDをURLで受け取り、結果や差戻先をJSONで受け取る設計としている。

	http
	
		POST /api/v1/proposals/1001/reviews
		Content-Type: application/json
	
	json
	
		{
			"action":"RETURN",
			"returnTarget":{
				"type":"REVIEW_STAGE",
				"stage":1
			},
			"comment":"提案内容の再確認をお願いします",
			"expectedVersion":3
		}

　リクエスト項目の定義は以下のようになる。

|項目名|型|必須|説明|
|---|---|---|---|
|proposalId|数値または文字列|URLで必須|提案ID|
|action|文字列|必須|`APPROVE`:承認、`RETURN`：差戻|
|returnTarget|オブジェクト|差戻時必須|差戻先指定|
|returnTarget.type|文字列|差戻時必須|`PROPOSAL_AUTHOR`または`REVIEW_STAGE`|
|returnTarget.stage|整数|審査段階への差戻時必須|審査段階|
|comment|文字列|要件による|コメント|
|expectedVersion|整数|推奨|画面表示時の提案バージョン|


##３－２．レスポンス仕様

　正常終了時は処理結果と更新後の状態を返す。

　例として審査を差し戻した場合

	http
	
		HTTPステータス:200 OK
	
	json
	
		{
			"reviewId": 5002,
			"proposalId": 1001,
			"action": "RETURN",
			"proposalStatus": "IN_REVIEW",
			"currentStage": 1,
			"returnTarget": {
				"type": "REVIEW_STAGE",
				"stage": 1
			},
			"reviewedAt": "2026-10-12T20:30:00+09:00",
			"version": 4
		}

|項目名|説明|
|---|---|
|reviewId|今回の審査ID|
|proposalId|提案ID|
|action|実行した審査操作|
|proposalStatus|更新後の提案ステータス|
|currentStage|指定された審査段階|
|returnTarget|指定された差戻先|
|reviewedAt|審査実行日時|
|version|更新後のバージョン|

###３－３．処理内容

　APIが内部で何をするか順番に記載する。

	１．認証確認：ログインユーザの特定
	２．権限確認：対象提案に対する審査権限があることの確認
	３．状態確認：提案が審査可能な状態であり、現在の審査段階が一致することの確認
	４．入力チェック：承認・差戻の値、差戻先、コメント、バージョンの検証
	５．審査履歴登録：審査者、審査段階、結果、コメント、日時、差戻先の記録
	６．状態更新：承認なら次段階へ進め、差戻なら指定先に応じて状態の変更
	７．操作履歴記録：変更前後の状態と操作情報を監査用に記録
	８．レスポンス返却：処理結果と更新後の状態を返す
	※データ更新は整合性を保つため、原則として1つのトランザクションで処理する。

###３－４．エラー仕様

|HTTPステータス|発生条件|例|
|---|---|---|
|400 Bad Request|入力値不正|審査段階の範囲外|
|401 Unauthorized|未認証|ログインしていない|
|403 Forbidden|権限なし|担当外の審査者が操作|
|404 Not Found|提案が存在しない|提案された提案IDが存在しない|
|409 Conflict|状態不一致|すでに審査済み、バージョン不一致|

　エラー時のレスポンス形式も統一しておくと、画面側で扱いやすくなる。

	{
		"error":{
			"code":"INVALID_REVIEW_STAGE",
			"message":"現在の状態では審査を実行できません"
		}
	}
